# 番茄女频爽文：开书与连写经验

这是作者和上一本书《重生换亲，我一眼看穿糙汉首富命》一起摸出来的做法。工具层面一律交给 oh-story 那套技能（`story-long-scan`、`story-long-write`、`story-deslop`、`story-review`、`story-publish`、`story-cover`），本文件只管三件事：**作者要什么**、**按什么顺序做**、**哪里容易出错**。

---

## 一、作者是谁、要什么（每次开工先对齐）

- 番茄女频，新人（Lv.0-1）。2026-10-12 起新人新书只能「完本签约」：整本写完、达到 15 万或 30 万字（按主分类，以建书页显示为准）才能申请，整本一次审、每本 3 次机会。所以：**一本书要在 15 万字左右讲完一个完整故事，坑全填上**。动笔前提醒作者去后台确认所选分类是 15 万还是 30 万门槛。
- 第一原则是**爆**：爽为主，节奏按短剧，每章至少一个爽点或强钩子，不铺垫不注水；要能改漫剧/短剧（画面感强、一集一个爽点）。
- 作者偏好年轻向：万人迷、系统偏爱、身份反差、豪门、校园、打脸。**不要**慢热年代文那种老派节奏。阻碍可以少，但冲突必须有——冲突是让女主表演的舞台，不是让她受苦的。
- 作者要**先看全书大框架**，同意后才排细纲；**每一章写之前先把这章的思路用几句白话给作者确认**，作者说行再写正文。连写多章时，可以一次把接下来 2-3 章的思路一起报给作者确认，确认后连写，每批最多 3 章。
- 汇报只讲故事：发生了什么、要作者定什么（给白话选项＋推荐）、下一步。不说脚本名、字段名、文件路径之外的工程词。
- 作者说「交给你定」「按推荐」「继续」时，可以按推荐拍板，但要在汇报里一句话说清替他定了什么，方便他改。

## 二、标准流程（按这个顺序，别跳）

1. **扫榜（可选但推荐）**：用 `story-long-scan` 扫番茄女频阅读榜、新书榜、书库最热新书。云端容器里：
   - 先 `npm install -g agent-browser`，再用自带 Chromium 起无头浏览器：`/opt/pw-browsers/chromium-*/chrome-linux64/chrome --headless=new --no-sandbox --remote-debugging-port=9222 --user-data-dir=<scratchpad>/chrome-prof --proxy-server="$HTTPS_PROXY"`（后台运行；每次新的 Bash 调用前先确认 9222 还活着，死了就重起）。
   - 采集脚本页面全空白 = 被番茄限流：换一个新的 `--user-data-dir` 重启浏览器再采。
   - 番茄网页版站内搜索经常搜不到书，找具体某本书用网页搜索拿到 `fanqienovel.com/page/{bookId}`，再 `curl` 那个页面解析 `__INITIAL_STATE__` 拿简介、字数、在读、章名。章节正文有字体加密，读不全，**不要**试图下载整本书。
2. **拆对标书**：`story-long-analyze` 需要作者提供 txt 原文。作者没给 txt，就只用公开的简介、标签、章名、在读数做「功能位」分析（核心梗、爽点节奏、人设反差、书名写法），**只借结构功能，不复刻人物、剧情、桥段原文**。
3. **定方向 → 定设定 → 全书大框架**：走 `story-long-write` 的开书流程（交给 story-architect 子代理出方案）。设定定完，先把**全书大框架**（分卷、每卷主要事件、主角得到什么、打谁的脸、结尾）用故事话给作者看，作者点头再出卷纲。
4. **每章**：细纲（story-architect，一批 1-3 章）→ **把这章思路几句话给作者确认** → 组装写手任务包（`build_writer_prompt.py`）→ 主会话填满 7 个槽位 → 交 narrative-writer 写 → `storyctl.py chapter check --fix-punctuation` → 修 → 提交追踪 → git 提交推送。
5. **每批 3 章写完**：交 consistency-checker 做跨章核对（钱账、时间、人物在场、伏笔），按结果修，改过正文的章用 `mode=revision` 补提交。

## 三、踩过的坑（照着避）

**写手与检测**
- 写手经常超字。任务包里写清「字数范围、宁短勿超」；超了就交写手「只删不加」压一次。
- 「不是……是……」「没有A，没有B」这类句式、比喻过密、细纲叙述原句搬进正文，检测都会点名：叙述句改写，角色台词保留并登记进细纲「原样出现的原话」。
- 写手爱自己加「前世记忆」「新人物」：对照设定，重复的、和前文冲突的删掉。
- 每章交稿后读一遍正文，盯住和前文的硬冲突（时间、钱数、谁在场、谁已经结婚/退场）。

**写作进度（tracking）提交**
- 本章 `character_changes` 里出现的每个人，`character_snapshots` 都要给完整快照，否则提交失败。
- `delta.result` 不超过约 120 字；`continuity_risks` 最多 5 条，多了合并；从 context 删掉的条目要放进 `retired_context_items`。
- 修订（revision）事务不能撤下 context 条目，要等下一章的 append 事务里再改。
- 用 Python 改 JSON 时别写 `null`（写 `None`）。
- 批末改了已提交章节的正文，要给那几章各补一次 `draft` + `chapter commit` 修订，否则开场 hook 会报「正文比状态卡新」。

**协作**
- 设定里留的「待作者定」要么问作者、要么在作者授权下按推荐定并写进 `设定/题材定位.md`「作者已定」，别让子代理反复挂起同一件事。
- 子代理会话没有对话记忆：作者在对话里定下的一切，交接前必须写进 `设定/`。
- git 每做完一步就 commit + push（push 偶尔 503，退避重试）。

**AI 率检测（朱雀）**
- 腾讯朱雀网页版会弹图片验证码，不能也不要自动绕过。要么请作者自己贴进去测、告诉分数，要么请作者提供朱雀 API 密钥后用接口测。不用错别字、乱码这类花招骗检测器，只靠改写句子降 AI 味（可配合 `story-deslop`）。

## 四、爽文写法要点（作者口味）

- **系统偏爱外化**：女主做什么，旁人都脑补「她这么做一定有道理」；规则对她网开一面（别人排队她不用排、规则制定者亲自迎接）。爽点落在「旁人的反应链」上：震惊 → 改口 → 讨好/害怕。
- **万人迷**：几个男主各有身份和反差，修罗场靠误会、争抢、护短制造；女主始终掌握主动，「好女孩得到名声，坏女孩得到一切」。
- **身份反差 + 隐藏**：女主有秘密（系统、头奖、真实身世）不能被发现——给每段剧情一个「暴露危机」的紧张感，再让她用本事化解，越化解越爽。
- **打脸要有铺垫**：先让看低她的人当众说狠话，再当众兑现反转；一章一个，不拖三章以上。
- **阻碍少、冲突多**：反派可以蠢可以跳，但每次跳出来都要让女主赢得更多（钱、名声、男主好感、家族地位）。
- **安全线**：女主和所有感情线角色都设定为**成年人**（校园写大学）；原主的悲惨经历只用闪回点到，不写露骨内容；不写真实品牌、真实人物。
